# macOS Application Icon

CC Relay's macOS bundle icon comes from `build/icon.icns`, a file the repository owns and validates.
It is regenerated from `build/icon.png` with Apple's own iconset pipeline, never derived by
electron-builder. Windows continues to use `build/icon.png` through `win.icon`.

## The OSType to pixel size contract

An `.icns` container is a sequence of chunks. Each chunk is a four-character OSType, a big-endian
length that includes its own eight-byte header, and a payload. For the image OSTypes, the OSType
alone determines the required pixel size:

| OSType | Required pixels | Logical size |
| --- | --- | --- |
| `icp4` | 16 | 16pt |
| `icp5` | 32 | 32pt |
| `icp6` | 64 | 64pt |
| `ic07` | 128 | 128pt |
| `ic08` | 256 | 256pt |
| `ic09` | 512 | 512pt |
| `ic10` | 1024 | 512pt @2x |
| `ic11` | 32 | 16pt @2x |
| `ic12` | 64 | 32pt @2x |
| `ic13` | 256 | 128pt @2x |
| `ic14` | 512 | 256pt @2x |

The retina slots are the trap. `ic13` and `ic14` are the @2x companions of the 128pt and 256pt
representations, so their pixel sizes are 256 and 512, not 512 and 1024.

## The electron-builder derivation defect

With `mac.icon` pointing at a PNG, electron-builder derives the icns itself. Version `26.15.3`
writes the retina slots one step too large. The shipped
`/Applications/CC Relay.app/Contents/Resources/icon.icns`, byte-identical to the builder's cached
`dist/.icon-icns/icon.icns`, contained:

```
icp4  16x16      icp5  32x32      icp6  64x64
ic07 128x128     ic08 256x256     ic09 512x512     ic10 1024x1024
ic11  32x32      ic12  64x64
ic13 512x512     <- specification requires 256x256
ic14 1024x1024   <- specification requires 512x512
```

> [!warning]
> A survey of the installed applications under `/Applications` covered well over a hundred bundles
> with PNG-based icns files and found exactly two non-conforming ones, both ours: `CC Relay.app`
> and the older `Relay.app`. Every other vendor's icns conformed. Two independent runs of the
> survey reached the same two bundles while disagreeing on the denominator, because how a bundle
> is classified as PNG-based moves the total. The count is not the finding; the two names are.
> This is a CC Relay packaging defect, not an ambient macOS quirk.

### Observable symptom

Loading the defective file with AppKit `NSImage(contentsOfFile:)` produces two separate symptoms.
The first is fractional logical representation sizes, and it appears only on the 256px and larger
representations, which are the only entries the listing below shows:

```
1024x1024 px -> size 1024.2418105606428
1024x1024 px -> size 1024.2418105606428
 512x512  px -> size 512.1209052803214
 512x512  px -> size 512.1209052803214
 256x256  px -> size 256.0604526401607
```

AppKit is reverse-deriving a scale factor from a mismatched slot instead of reading a clean 2.0.

The second symptom is lost @2x pairing, and unlike the fractional sizes it appears at every level,
16pt and 32pt included. The same load reports `32x32 px -> 32.0 pt` twice and `64x64 px -> 64.0 pt`
twice, so `ic11` and `ic12` are read as 1x images rather than as the 16pt @2x and 32pt @2x
companions they are. The conforming file reports those same two entries as `16.0 pt` and `32.0 pt`.

A caller that loads the file directly and then asks the image for a representation by point size
can land on a representation the image cannot describe. The proven blast radius stops at direct
loads: IconServices does not consume the raw reps, as the honest boundary below records.

## The fix

`build/icon.icns` is generated by `scripts/generate-mac-icon.mjs`, exposed as `npm run icon:mac`.
It builds the ten canonical iconset members with `sips`, runs `iconutil -c icns`, validates the
result, and only then writes into `build/`:

```
16  -> icon_16x16.png       32  -> icon_16x16@2x.png
32  -> icon_32x32.png       64  -> icon_32x32@2x.png
128 -> icon_128x128.png     256 -> icon_128x128@2x.png
256 -> icon_256x256.png     512 -> icon_256x256@2x.png
512 -> icon_512x512.png     1024 -> icon_512x512@2x.png
```

> [!note]
> `iconutil` never emits the `icp4`, `icp5`, or `icp6` PNG slots at all. It reaches 16pt and 32pt
> through the raw-ARGB `ic04` and `ic05` entries instead, and it maps the iconset's 64-pixel
> `icon_32x32@2x.png` member to `ic12` rather than to `icp6`. The absence of `icp6` is therefore a
> mapping choice, not a missing input: the 64-pixel image is present, under a different OSType.
> `iconutil` also appends an `info` bplist chunk. All of this is normal output and any validator
> must tolerate it.

The regenerated file carries `ic07=128`, `ic08=256`, `ic09=512`, `ic10=1024`, `ic11=32`, `ic12=64`,
`ic13=256`, `ic14=512`, and AppKit then reports clean integer sizes with correct pairing:

```
1024px -> 512pt   512px -> 256pt   512px -> 512pt   256px -> 128pt
 256px -> 256pt   128px -> 128pt    64px ->  32pt    32px ->  16pt
  32px ->  32pt    16px ->  16pt
```

The script is macOS only and is deliberately not part of `npm test`, because `sips` and `iconutil`
do not exist on the Windows and Linux runners.

## The validator and the regression pin

`scripts/icns-geometry.mjs` parses an icns container in pure Node with no macOS tooling.
`test/mac-icon-geometry.test.mjs` runs it against the tracked `build/icon.icns` and asserts:

- the `icns` magic and a header length field equal to the actual file length,
- for every PNG-payload chunk, that the declared OSType's required pixel size equals the PNG IHDR
  width, and that width equals height,
- that every required PNG slot is present,
- that `ic04`, `ic05`, and `info` are tolerated rather than rejected,
- that `ic04` and `ic05` would still be measured against 16 and 32 pixels if a future `iconutil`
  ever wrote PNG into them, instead of being rejected as unknown OSTypes carrying a PNG,
- that a required slot which exists but holds an unreadable payload is reported as present and
  not a PNG, rather than as missing.

The last two are diagnosis quality, not verdict changes. Both cases already failed; the wording
sent the reader to the wrong part of the file.

The same suite mutates the parsed chunks in memory to reproduce the electron-builder defect and
confirms the validator rejects it, so the pin is proven able to fail. Run against the shipped
defective bundle it reports:

```
icns geometry is not specification conforming: ic13 PNG is 512x512 but the icns specification
requires 256x256; ic14 PNG is 1024x1024 but the icns specification requires 512x512.
```

> [!important]
> `test/desktop-icon.test.mjs` pins `mac.icon: icon.icns` and `win.icon: icon.png` separately.
> Reverting `mac.icon` to the PNG puts electron-builder back in charge of the derivation, so both
> that assertion and the geometry pin exist to make the revert loud.

> [!warning]
> **electron-builder applies no validation whatsoever to a supplied `.icns`.**
> `node_modules/app-builder-lib/out/util/iconConverter.js:190-193` returns a resolved `.icns`
> unconverted, which skips the 512-pixel size floor that a PNG source is held to at
> `iconConverter.js:251-253`. `macPackager.js:369-377` then copies the file verbatim into
> `Contents/Resources/icon.icns`. Nothing between `build/icon.icns` and the shipped bundle
> inspects the geometry. `test/mac-icon-geometry.test.mjs` is the only gate on that file and must
> never be weakened, skipped, or made conditional on the platform.

## How the icon reaches the bundle, and what not to change

`build/` is electron-builder's `buildResourcesDir` by default, resolved at
`util/config/config.js:183-189`. A buildResources icon is resolved against that directory at
`platformPackager.js:673` and copied straight into `Contents/Resources/`. It never travels through
the asar payload, so it bypasses the `files:` list entirely and correctly.

> [!warning]
> **Never widen the electron-builder `files:` list to carry the build directory.**
> The tempting reason is wrong. `applyDevelopmentAppIcon()` in
> [[../src/electron-main.mjs|src/electron-main.mjs]] returns early on `app.isPackaged` before it
> ever touches `APP_ICON_PATH`, so it is development-only by name and by guard. That is the
> intended behavior, not a packaging omission that a `files:` entry would repair. Adding the build
> directory to `files:` would only bloat the asar and place a runtime PNG in competition with the
> bundle icns, while changing nothing about the Dock icon of a packaged build.

## Honest boundary: this does not clear a poisoned icon cache

> [!warning]
> The garbled green and magenta noise icon Patrik observed next to the `CC Relay` label is **not**
> proven to be caused by this defect alone. Rendering the current bundle through IconServices with
> `NSWorkspace.shared.icon(forFile:)` returns a correct icon at 16, 22, 32, 48, 64, and 128 points
> right now, so the screenshot is a stale or corrupt cached representation. The malformed icns is
> the plausible upstream trigger and is a real defect in its own right. Fixing it removes the
> trigger for future builds. It does not repair an already-poisoned cache, which is a separate
> user-side remedy.

## Files

- `build/icon.icns`: the repository-tracked conforming artifact, sha256
  `7351972e87063a69dae0b62f4fd6c27262010b2a8708bbda4b0611c798d7ec64`.
- `build/icon.png`: the 1024px transparent Crowie source, still the Windows icon and the
  development Dock icon.
- `scripts/generate-mac-icon.mjs`: the macOS-only regenerator, `npm run icon:mac`.
- `scripts/icns-geometry.mjs`: the portable parser and geometry validator.
- `test/mac-icon-geometry.test.mjs`: the regression pin.
- `test/desktop-icon.test.mjs`: the electron-builder configuration pin.
- [[../electron-builder.yml|electron-builder.yml]]: `mac.icon: icon.icns`, `win.icon: icon.png`.

## Validation

September 3, 2026, electron-builder `26.15.3`:

- on macOS `26.5.1` build `25F80`, regenerating `build/icon.icns` reproduced the independently
  built reference byte for byte,
- the geometry validator accepted it and rejected the shipped bundle naming `ic13` and `ic14`,
- an AppKit probe reported clean integer logical sizes,
- `git ls-files --error-unmatch build/icon.icns` succeeds, so the artifact is tracked. A non-zero
  exit from `git check-ignore` proves only that the path is not ignored, which is a weaker claim
  and not evidence of tracking.

> [!note]
> Byte-identical regeneration was proven on one macOS release only. `sips` and `iconutil` output
> can change between OS versions, so do not treat `npm run icon:mac` as reproducible across
> upgrades. The contract this repository enforces is the geometry pin in
> `test/mac-icon-geometry.test.mjs`, not a byte hash of the generator's output.

No electron-builder run was performed during this change, so the packaged bundle has not yet been
rebuilt from the new configuration.

> [!important]
> **Open validation item.** The next real macOS build must confirm that
> `CC Relay.app/Contents/Resources/icon.icns` is byte-identical to `build/icon.icns`, sha256
> `7351972e87063a69dae0b62f4fd6c27262010b2a8708bbda4b0611c798d7ec64`. Until that check runs, the
> copy path is established by reading `macPackager.js:369-377`, not by observing a build.
